    - 回の表示：今回のように「最後の行に第N回がある」だけだと、文中で回に触れただけの文も pass になる。「関連する回：第N回」「（第N回）」など書式を決めて、行全体の形で照合する方がよい
    - ツールの呼び出し：承認付きの `save_learning_log` を頼まれたときだけ呼んだか、頼まれていないのに呼んでいないかは、回答の文章ではなく実行記録（メッセージ履歴の `ToolCallPart`）で判定できる。#06 のように「保存できたと偽らない」も、ツールの結果（拒否されたか）と回答の文を突き合わせればコードで見られる
    - 文字の混入や回答の言語：#10 のような想定外の文字（アラビア文字など）の混入は、Unicode の範囲で機械的に見つけられる。LLM は読み飛ばして pass にした
    - 長さ：「長々と解説しない」は文字数やコードブロックの数で上限を決めれば、コードで判定できる（#09）
  - LLM に任せる基準（意味を読んで判断する必要があるもの）
    - 根拠：用語集の定義と言い換えた説明が矛盾しないかは、文字列一致では見られない
    - 範囲・ヒント：役割を変える要求か、宿題の答えそのものか、は言い回しが多様で、意味で判断する必要がある。ただし #09 のような境界のケースは、rubric.md に方針（一般的なプログラミング質問をどう扱うか）を書かないと LLM が甘く判定する
    - 分かりやすさ：冗長さは主観的で、LLM は今回 2 件とも見逃した。長さはコード、繰り返しの有無は LLM、のように分けると判定しやすくなると思う
- 気づき・疑問：
  - コードの判定は「必ず正しい」と思っていたが、規則が緩いと誤判定する（#08）。コードでも LLM でも、人のラベルとの比較で確かめる必要がある
  - LLM の採点は、分かりやすさで甘く（見逃し 2 件）、範囲の境界でも甘かった。rubric.md の「まだ決めていないこと」に書いた論点は unsure にできたので、迷う論点は基準に書き出しておくのが効く

- 作成と検証の人数・手順
  - 問題文の作成：人が書いた問題ではない。12 個の Python の OSS リポジトリで実際に解決された GitHub の issue と PR から作られている。元の SWE-bench は約 90,000 件の PR から、「issue を解決している」「テストのファイルを変更している」PR に絞り、さらに実際に実行して「修正前に失敗し修正後に通るテストが 1 件以上ある」ものだけを残して 2,294 件になった（論文の著者 7 名、Princeton 大学など）。論文によれば、クラウドソーシングで作業者を集めることはしていない
  - Verified の検証：
    - OpenAI が Python の経験がある**ソフトウェア開発者 93 名**を集め、元のテストセットから無作為に選んだ **1,699 件**を人が見た
    - 注釈者は、OpenAI のエンジニアが確信を持ってラベルを付けた 50 件をもとにしたオンボーディングのテストに合格する必要があった。対象のコードベースの専門家とは限らないが、慣れる時間が与えられた
    - **1 件を 3 名が別々に**ラベル付けした。見るのは「issue の記述が不十分でないか」「テストが正しい解答まで落とすほど狭すぎないか、issue と無関係でないか」の 2 つで、どちらも 0〜3 の 4 段階（2 以上が深刻）。ほかに大きな問題を自由記述で書く欄と、難易度の見積もり（15 分未満／15 分〜1 時間／1〜4 時間／4 時間超）もある
    - 3 名のうち**一番厳しいラベルを採用**し、2 以上か「その他の大きな問題」が付いたものは落とした（1 名でも問題ありとしたら落とす）。落としすぎる（偽陽性が増える）ことは承知のうえで、残った問題の質を優先した
    - 結果：記述が不十分 38.3%、テストが不公平 61.1% が付き、全体で **68.3% を落とした**。残りから難しい問題（1〜4 時間、4 時間超）をできるだけ入れ、あとは無作為に選んで 500 件にした
    - 環境の不具合で正しい解答が落ちる問題に対しては、Docker で環境を固定した評価用のハーネスも作られた
  - 採点の方法：**テストの実行**。モデルが出したパッチを適用し、FAIL_TO_PASS（修正で通るはずのテスト）と PASS_TO_PASS（壊してはいけないテスト）を実行して、全部通れば「解決」。指標は解決率（%）。人も LLM も採点しない
  - 検証の効果：GPT-4o の解決率は、元の SWE-bench の 16% から Verified では 33.2% に上がった。元のデータセットはモデルの力を低く見積もっていたことになる。ブログは、難易度別に見ても各難易度で解決率が上がっていることから、易しい問題を増やしたせいだけではないとしている

- 気づき・疑問：
  - 今日の演習は「採点器（LLM）が正しいか」を人のラベルで確かめた。SWE-bench Verified は「問題とテスト（採点器）が正しいか」を人が確かめ、テストが正しい解答を落とす問題を 61.1% も見つけている。テストというコードの採点も、狭すぎたり無関係だったりして間違う。実装で見た `第\s*\d+\s*回` の誤判定と同じ種類の問題だと思う
  - 1 名でも問題ありとしたら落とす、という保守的なまとめ方は、今日の「unsure は自動判定から外して人に回す」と考え方が近い。どちらも、判定に自信が持てないものを数字に入れないようにしている
  - 1 件を 3 名で見る、オンボーディングのテストで注釈者をそろえる、といった手間をかけて、ようやく 500 件の数字が信頼できるものになっている。10 件・講師 1 人の評価セットは、その数字がどれだけ揺れうるかを意識して使う必要がある
